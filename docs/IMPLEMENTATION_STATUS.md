### Transport security

- HTTPS enabled with a self-signed certificate (no domain registered yet): `nginx/nginx.prod.conf` is now actually mounted by `docker-compose.yml` (it existed before this pass but was never wired in — `nginx.conf` was mounted instead, meaning the whole HTTPS/redirect config had been dormant and unexercised). Port 80 now 301-redirects to 443; TLS terminates at nginx with the same security headers as before. `ops/tls/generate-self-signed-cert.sh` generates/regenerates the cert (`nginx/certs/`, gitignored — private key material) and accepts a common name + validity period, so swapping in a real domain later is just re-running it with that domain and, ideally, replacing the self-signed cert with a CA-issued one (e.g. Let's Encrypt) instead. Fixed a real bug in `nginx.prod.conf` before activating it: it used static `upstream {}` blocks for `server-api`/`dashboard`, which nginx resolves once at startup and never again — `nginx.conf` already had a fix for this exact problem (a `resolver` directive + `set $var` indirection forcing re-resolution every 10s), ported over so the newly-activated prod config doesn't silently start proxying to stale container IPs after a restart. Verified live: HTTP→HTTPS redirect, a full login + authenticated API call + dashboard load round-trip over HTTPS, and the deployed certificate's subject/SAN/validity via `openssl x509`.
- Fixed the endpoint agent (`agent/`) for compatibility with the above, since this dev environment's `agent-demo` talks to `server-api:8000` directly on the internal docker network and so never exercised either failure mode: the Go HTTP client had no TLS configuration (would fail every request against a self-signed cert with `x509: certificate signed by unknown authority`) and no redirect policy (Go's default silently downgrades a POST to a GET on a 301, which is exactly what nginx now returns for a plain-HTTP request — meaning a misconfigured agent would silently stop sending logs/heartbeats with no error at all). Added `server.insecure_skip_verify` (config field + `AGENT_INSECURE_SKIP_VERIFY` env var) and a `CheckRedirect` that fails loudly instead of following any redirect. ### Threat intelligence and OCSF

- Provider-normalized caching shipped: `worker/worker/ti/cache.py` caches every TI provider lookup (VirusTotal, AbuseIPDB, OTX, GreyNoise, Shodan, URLhaus, WHOIS, GeoIP) in Redis, keyed per tenant/provider/lookup-type/indicator, with a provider-specific TTL (900s-24h depending on volatility). A live-fetch failure now falls back to a stale cached copy (retained at 4x the fresh TTL) rather than failing enrichment outright, and only propagates the error when there is truly no cached copy at all. Wired into `EnrichmentAggregator` (all four `ingest_ip`/`ingest_domain`/`ingest_hash`/`ingest_url` provider-gather paths) and its `ai_analyst.py` call site.
- Versioned OCSF mappers shipped: `worker/worker/ocsf_mappers.py` covers Windows authentication/process, Linux auth, firewall/network, DNS, proxy/web, cloud audit, and endpoint/FIM, each producing correct `class_uid`/`category_uid`/`activity_id`/`activity_name`, canonical entities, and an `unmapped_fields` diagnostic listing every input field the mapper didn't recognize, plus a generic Base Event fallback for anything else. Wired into the real ingestion path: `worker/worker/event_normalizer.py` previously hardcoded `class_uid: 1001`/`category_uid: 1` for every single event regardless of type; it now dispatches by ECS `event.category` (authentication/process/network/dns/web/http/iam/api/file), since decoder *names* are user-configurable and carry no fixed taxonomy while `event.category` is the one field every decoder is asked to populate. 16 golden-fixture tests per family plus dispatch/fallback coverage.
- IOC propagation shipped: `ioc_observations` (indicator, type, confidence, verdict, source, first/last seen, tenant-scoped, unique per group+indicator+type) and `ioc_links` (which event/alert/rule/case an indicator was seen on) tables. `record_enrichment_iocs` persists every IOC an enrichment pass surfaces and links it to the alert, called from `ai_analyst.py` right after enrichment succeeds (best-effort — a persistence failure logs a warning and does not block triage). A later low-confidence observation of an already-known indicator bumps `last_seen` but never downgrades a higher-confidence verdict. `GET /api/iocs/{indicator}` (new, `iocs:read`-guarded, tenant-scoped with the standard superadmin `?group_id=` override) gives an analyst a pivot view of an indicator's observations and links; a foreign-tenant or unknown indicator returns `404`. OpenAPI operation count is now 153. A real bug was found and fixed during live verification: the raw-SQL upsert/link inserts did not supply an `id` column value — the table's `id` default is Python-side on the ORM model (`default=uuid.uuid4`), which a raw `INSERT` bypasses entirely, so the very first insert for any new indicator failed on a NOT NULL violation; fixed by generating the UUID explicitly in `ioc_store.py` before both inserts.

### Investigation workspace

- Unified cursor-paginated case timeline shipped: `GET /api/cases/{case_id}/timeline` was previously nearby-alerts-and-alert-notes-only (fixed ±24h window, no pagination, capped at 50 alerts). It now also merges case notes (previously only alert notes appeared), FIM events on the triggering alert's agent, TI/IOC enrichment linked to the alert (via the `ioc_links`/`ioc_observations` tables from this session's earlier threat-intel work), and SOAR execution steps for any run triggered by the alert (currently always empty in practice — see Known Limitations). Item assembly was refactored into a shared `_build_case_timeline_items` helper so the same logic backs both the paginated route and the new chain-of-custody export below. Pagination is an opaque base64-encoded offset cursor (`next_cursor` in the response, `null` once exhausted) — kept backward compatible with the existing dashboard `CaseDetailPage`, which ignores the new fields and keeps working unpaginated at the (generous) default `limit=100`.
- Entity pivots shipped: `GET /api/entities/{entity_type}/{entity_value}` (new, `logs:read`-guarded, tenant-scoped with the standard superadmin `?group_id=` override) returns every alert and case touching an IP or hostname, plus UEBA risk score/anomaly history for any UEBA-tracked entity type (`ip`, `hostname`, or others like `user` that have no direct `Alert` column — those pivot on UEBA data alone). A foreign-tenant or entirely-unknown entity returns `404`.
- Saved queries and bookmarks shipped: `GET/POST/DELETE /api/saved-queries` and `GET/POST/DELETE /api/bookmarks` (new `saved_queries`/`bookmarks` tables), authenticated-only (no new permission). Each caller sees their own rows plus any other tenant member's rows marked `is_shared`; only the owner may delete or update. Creating a bookmark for an already-bookmarked entity updates it in place (unique per owner+entity_type+entity_id) rather than erroring or duplicating.
- Signed chain-of-custody incident export shipped: `GET /api/cases/{case_id}/export` bundles the case, its full (unpaginated) timeline, and every alert referenced in that timeline; each of the three sections gets its own SHA-256 "artifact hash" and the whole bundle is signed with HMAC-SHA256 (`app/services/custody_export.py`), so a per-section change is independently detectable, not just an overall "tampered" flag. `POST /api/exports/verify` re-derives the signature and every artifact hash from the bundle alone (no database lookup), so it can verify an export handed back long after the case — or even the exporting tenant — has changed. Added a dedicated `EXPORT_SIGNING_SECRET` setting (deliberately separate from `JWT_SECRET` for key separation), falling back to a domain-separated hash of `JWT_SECRET` when unset so exports work out of the box in dev. The export action is audited (`case_exported`). Verified live end-to-end through nginx against a real case: untampered bundle verifies valid; mutating one section (`case.severity`) flags only that section invalid while `timeline`/`alerts` remain independently valid, and the outer `signature_valid` correctly flips to `false`. OpenAPI operation count is now 160.
