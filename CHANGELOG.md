### Added

- **Compliance Manager — OS-level hardening checks** (GravityZone-style endpoint posture, per `docs/superpowers/specs/2026-09-08-compliance-os-hardening-design.md`): the agent now runs 16 real CIS-Benchmark-style checks locally on each Linux endpoint — account/password policy (max age, complexity, lockout, empty passwords, duplicate UID 0), network/firewall hardening (active firewall backend, IP forwarding, legacy insecure services), SSH hardening (root login, password auth, protocol, MaxAuthTries), and kernel/filesystem hardening (ASLR, ptrace scope, core dumps, `/tmp` mount options) — new `agent/internal/hardening/` package, reported alongside the existing hygiene snapshot (`hygiene_snapshots.hardening_checks` JSONB column). Compliance Manager's two existing shallow checks (`local_account_hygiene`, `open_ports_hardening`) now aggregate this real per-check data instead of a coarse proxy, and two brand-new controls (SSH hardening, kernel hardening) were added to all three frameworks (ISO 27001, PCI-DSS, SOC 2) — 8 controls per framework now, up from 6. Hosts on an older agent version fall back to the original shallow logic, so nothing regresses. Every check treats a missing config file as `not_applicable`, never a fabricated `pass`/`fail`; a privileged-read failure (e.g. `/etc/shadow` unreadable) reports `error` distinctly. Built via subagent-driven-development (9 tasks, full TDD with `t.TempDir()` fixtures, 17 Go tests). Found and fixed two real bugs during the process: (1) a task's commit accidentally swept in unrelated uncommitted work sitting in the same files (the Compliance Manager and Situation Brief caching features from earlier in the session) — caught by task review, fixed via git surgery to cleanly separate the commits; (2) `GET /api/hygiene/latest`/`GET /api/hygiene/{agent_id}` 500'd after deployment because a manual serialization helper (`_snap_out` in `hygiene.py`) wasn't updated to include the new field — found during live verification, not caught by the plan (a genuine gap in the plan itself), fixed directly. Verified live on production against WAF-SERVER (`socwaf.solusi247.com`): real gaps surfaced for the first time — SSH root login permitted, password auth enabled, no failed-login lockout, IPv4 forwarding on — dropping its ISO 27001 score from a previously shallow 83% to a more honest 38%. Agent packaging version bumped to 1.3.0 for this release (see also the version-injection fix below). Linux-only for v1; the `Check`/`Report` types are deliberately OS-agnostic so a future `windows.go` collector needs no schema change.

- **Fixed a real production incident: DB transactions held open across slow LLM calls, blocking migrations and live alert ingestion**: `assistant.py`'s SOC Assistant tool-calling loop, `situation_brief.py`'s AI brief, `reports.py`'s PDF narrative, and `worker/hunter.py`'s threat-hunt analysis all queried the DB and then called out to 9router (which can take 60-90s+ under its documented retry/backoff behavior) while still holding that query's transaction open. Discovered when a slow assistant conversation held a transaction open long enough to block an in-flight `ALTER TABLE` migration during a routine deploy, which cascaded into stalled `alerts`/`cases` inserts — real customer WAF traffic backed up for several minutes before the stuck sessions were found via `pg_stat_activity` and terminated. Fixed by committing the read transaction immediately before each LLM call in all four call sites (worker's other LLM call sites — `ai_analyst.py`, `ai_consumer.py`, `report_sender.py` — already scoped their sessions correctly and needed no change). Verified locally: an assistant call with a real ~11s 9router retry sequence left zero `idle in transaction` sessions behind afterward, versus the multi-minute stuck sessions seen during the incident.
